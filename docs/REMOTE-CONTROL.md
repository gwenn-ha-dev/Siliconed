# silicontrol, the remote control of Siliconed: how it works

**The reference is in the app.** `silicontrol help` gives the overview, `silicontrol help <command>` or `silicontrol <command> --help` one page, `silicontrol help all` the whole reference (contract, JSON answers, error codes, recipes). To put an agent to work, tell it “look at `silicontrol help`”. This file only explains how the thing is built; it does not repeat the help, so the two cannot diverge.

## The idea

The open app holds the machine's only render queue. `silicontrol …` adds to it, waits, stops, reads the history: the same functions as the buttons (`AppState.enqueue`, `cancel`, `remove`, `stopAll`). What the command adds shows up in the window; what the mouse starts, the command sees. There are never two engines inside the Mac's memory. When the window computes on another Mac (Render › Compute On), the commands follow it: they still talk only to this Mac's socket, but act on the other Mac's queue and history, as the buttons do; `install`, `import` and `start-image` refuse there, as do `rewrite` and `describe` (the writer is this Mac's) and `uninstall` and `library move|home` (the files are the other Mac's, and so is the click); `install stop` stops the lender's installation there, or the upload of a file sent from this Mac.

**A license is accepted only in the window.** A job whose model's license the library does not record is refused by the engine (`license_not_accepted`) and set aside, out of the queue, while the app's sheet shows the license: `status` lists it under `"waiting_for_license"`, `wait` waits for it, `cancel` removes it. Accepted, it goes back to the head of the queue; declined, it ends in `"error"`. No command accepts on the user's behalf.

**A prompt's alternatives expand the same way on both sides.** `"woman posing in a {library|greenhouse}"` makes two jobs, at the same seed, whether the prompt comes from the app's field or from `silicontrol add`: both go through `PromptAlternatives` (the library, `App/Sources/Siliconed/PromptAlternatives.swift`), then through `AppState.enqueue`. The server redoes nothing: it refuses what the parser refuses (error `prompt`), and each job carries its expanded prompt and its `choices`. The syntax and the answer are in `silicontrol help add`.

**A grid is jobs; its sheet is an export.** `silicontrol grid --x … [--y …]` and the window's series (« Generate » with something bracketed, `App/Sources/SiliconedApp/Series.swift`) both check the grid with the library (`RenderGrid`, `App/Sources/Siliconed/RenderGrid.swift`) and queue it through `AppState.enqueueGrid`: one ordinary job per cell, in the sheet's reading order, plus a `GridRun` that only remembers which job is which cell (`App/Sources/SiliconedApp/Grid.swift`). The axes are a `{…}` group of the prompt, the seed, the steps, a LoRA's strength, LoRAs to compare (`loras=none,flat,ink`: one added to the stack per cell, names resolved as `--lora` does), the model (`model=z-image,qwen-image-2.1`: each cell at its model's own steps, refused with a `--lora`), the edit's images (`image`: each `--ref` alone, with the same instruction), the solver, the starting image's strength (`start=`) and Detail (`detail=`). Each cell is a finished image that joins the history; the run holds no pixel, and finds its cells there by their job (`cell(of:)`). **The sheet is never an image of the history**: it is drawn off the main thread only when asked, into a file — `sheet g2 FILE.png|FOLDER` (« Export Sheet… »), or `grid --wait --out D` and `wait g2 --out D`, which write it into `D` once the last cell has ended (done, failed, stopped or removed), with a `"type": "sheet"` line that carries its path (`--no-sheet` skips it). The `Signal` `.gridEnded` tells them the last cell ended. A cell that did not render is drawn empty, with why; no cell rendered, no sheet. A `{…}` group on no axis is refused (`grid`), never multiplied. The syntax is in `silicontrol help grid`.

**The window's series are the same grids.** What varies — the prompt's groups, the Seeds, the knobs bracketed (`Bracket`, its pure rules in `App/Sources/Siliconed/SeriesLayout.swift`) — lays out on two axes at most, and « Generate » renders it through `enqueueGrid`: the same cells, the same images, bit for bit, as `silicontrol grid`. Every series of the session is kept (`AppState.series`): in the history its tile heads its cells (`StripRow`), and the canvas lays them out (`SeriesCanvas`). Seeds alone is a series too. Neighbouring cells of a series that differ only by their seed render in one pass, each its own job (`AppState.train`), and an encoded prompt is kept for the renders that follow (`RenderCache`). `grid` gives the window its axes as a series where the window has them (`setSeries`); `reuse` answers the rack's series (`"series"`, its axes as `--x` and `--y` read them).

**Variations are the menu's.** `silicontrol vary i7 subtle|strong [--batch N]` and an image's “Variations” menu (the button under the image, its context menu) both call `AppState.vary`: as many ordinary jobs as the rack's “Seeds” (1 by default; `--batch` overrides it), with exactly that image's settings and seed, each adding one variation seed drawn at random (`Request.variations`, `App/Sources/Siliconed/Variation.swift`) at the family's strength (`Variation.Amount`), never a number the command passes. A variation of a variation appends to the chain, so it varies *that* image. Refused on an enlargement or a crop, or a model that is not ready (`model`). Each image's `variation` lists its variation seeds in order; `silicontrol help vary` has the answer.

**Enlarging is the menu's too.** `silicontrol enlarge i7 [--download]` and “Enlarge ×4” both call `AppState.enlarged`: macOS's super-resolution (VideoToolbox, macOS 26), no prompt, outside the queue — refused while a render runs —, answered with the new image once it is in the history. Apple's model is downloaded by macOS only with `--download` (else `download_required`); `silicontrol help enlarge` has the rest.

**A size is `WxH` or a proportion and a resolution.** `silicontrol add` and `grid` take `832x1216` as ever, or `3:4@2K`: the proportion (1:1, 4:5, 3:4, 2:3, 9:16, 5:4, 4:3, 3:2, 16:9), `@`, then `1K` or `2K`. Neither character means anything to a shell, so no quotes. It resolves to the pixels of the rack's Size in Two Scales (`SizeScales`, one function for both), whether or not that Beta option is on, and is refused (`format`) with its reason where the rack greys it: Anima's 2K, for instance, is the square alone (2048 px a side). The table is in [the app's page](APP.md#create).

**Solvers follow More Solvers.** `--solver` is accepted only with More Solvers on (Settings › Advanced › Beta) and on a model that offers more than Euler; otherwise the answer is a refusal (`solver`) that names the setting.

**Nothing depends on a click, except pairing.** What the window does, a command does too, **by the same functions as the buttons** (`AppState`, the Prompt Lab's `LabModel`), never by a road of its own. What stays in the window on purpose: pairing a Mac, accepting a license, “Lend This Mac” and “Forget”. The Prompt Lab — the Text and Images boxes at the head of the chain's column — is `lab`: what it holds and whether the column is unfolded, an image in as a drop brings it, with the role a newcomer takes (`lab add`, `rack.addInput`), a role (`lab role N edited|reference|start|none`, `rack.setRole`, refused where the rack's model lacks it, as the image's menu does not offer it), an image out (`lab remove`), its text as typed (`lab text`) and a click on its “Generate” (`lab generate`, refused with the button's own sentence when it is greyed); its answer gives each image's role and whether the next render reads it (`"used"`, `"unused"`). Its two buttons are `lab rewrite` and `lab describe N` (`LabModel.rewrite`, `describe`): the column unfolds, the button is pressed, and the text is written in the field token by token with its marks, as the click writes it, ⌘Z included — where `rewrite` and `describe` (below) answer on the socket and leave the field alone. They answer as soon as the writer starts (`lab` then says where it stands, `"writing"`), or with `--wait` once the text is written; the gesture is the window's, so a client that hangs up leaves it writing. Their refusals are `rewrite`'s, and `empty_text` for a text with nothing to rewrite. Its subjects are `subjects`. The starting image is `start-image`: an image of the Lab given the start's role, and its strength, a setting of the rack. Siliconed › Settings… is `settings [general|macs|lab|advanced]` (`SettingsWindow.show`, the panes named in the library, `SettingsPane`), and `settings lab [rewrite|describe] [--for ID]` opens Prompt Lab on one instruction, as the Lab's “Your Instruction” does (`showInstruction`). A knob's yellow ± is `bracket seed|detail|solver|start|loras` or `bracket lora NAME` (`app.bracketing`, as the click sets it): its bubble opens beside it, refused where the window draws no ± that would open; `bracket close` closes it. The rack's scroll is `rack top|dit`: its head, or the DiT's settings with the chain pinned in small above them; `rack fold|unfold` folds its column away and back (⌥⌘R, `RackColumnModel`); folding stops a Rewrite or a Describe under way. `rack detach|dock` are the toolbar's « Detach the Chain » and « Dock the Chain » (`RackColumnModel.setDetached`): the column in a floating window of its own, and back. `zoom in|out|fit` is View › Zoom In, Zoom Out, Zoom to Fit (⌘+ ⌘− ⌘0, `AppState.zoom`, the menu's gesture): on a series' cells or on the image, whichever the canvas shows; where the item is greyed nothing changes. `snapshot FILE.png` gives a window drawn by the app itself into a PNG: it is not a screen capture, so no permission is asked and the command works from a session without a display. The Prompt Lab's writer and Settings' switches are described next, and after them the gestures of the history, the series, the models, Compute On and the library.

**The Prompt Lab's writer is the window's.** `silicontrol rewrite "<text>" [--for ID]` and `silicontrol describe <image|i7> [--for ID]` call what the Lab's two buttons call: `LabWriter` over `PromptWriter`, in the engine's process (`EngineWorker`), our instructions per model and gesture (`PromptWriterInstructions`), the image read as the Lab reads a dropped one (`PromptWriterImage`), and for a model that reads images the `@names` put aside and put back (`LabInputs.MentionGuard`, shared as `LabModel.rewriteInput` and `rewritten`). The model it writes for is the one the Lab would take (`WriterTarget.pick`: the rack's, else the first installed) unless `--for` names one. The refusals are the Lab's, in its order (`WriterPause.decide`, one rule for the sentence under its buttons and for the code): the window follows another Mac (`remote`), an image renders (`busy`), no installed model carries a writer (`writer_absent`); and a second gesture while one writes (`writer_busy`), from the terminal or from the window. Nothing else is checked before: the engine plans the memory when the gesture runs, and a Mac where no plan fits says so then (`insufficient_memory`). The lines are `{"type": "started"}`, `{"type": "loading", "fraction"}` and `{"type": "text", "text"}`, which carries everything written so far (cumulative, as the Lab's stream is: the detokenizer may revise its last word); the verdict has the whole `text`, the `tokens`, and the `notice` and `lost_mentions` when the writer lost an `@name`. **A render that starts stops the gesture** (`stopped`), as it stops the Lab's. **A client that hangs up cancels it**: `Connection.isGone` sees the close without writing to the socket, and `LabModel.cancelRemote` ends the stream, whose termination stops the sampling (`LabWriter.write`) before the weights go back. Incognito: the text goes out on the socket and nowhere else. The writer is Qwen-Image-2.1's text encoder, which writes as installed: it is there once that model is (`silicontrol install qwen-image-2.1`), with nothing else to download, and `status` says so (`"writer"`). Both gestures act on this Mac: with the window on another one they are refused (`remote`). `silicontrol instructions` is Settings › Prompt Lab: what the writer is told for each model and gesture, listed, shown, replaced (`--set`, `--file`) or restored (`--restore`), through the same `LabModel.instructions` the pane's field writes (`PromptWriterInstructions.Edits`); the instructions are this Mac's too, and stay allowed with the window on another one.

**The Beta options are Settings' switches too.** `set beta [OPTION on|off]` writes the property each of Settings › Advanced › Beta's four switches is bound to (`developerMode` for More Solvers, `stepsBeta` for Choose Steps, `sizeScalesBeta`, `negativeLoRAStrengths`), so their `didSet` do what a click does, without waiting for the queue to be empty; `status` gives them as `"beta"`. They are this Mac's preferences, and the copy of the mirror the window shows is set with them. `set neural-engine [on|off]` is Settings › General's Neural Engine switch, on by default (`AppState.neuralEngine`): the engine gives the Neural Engine the work it does faster on this Mac, off the GPU alone; alone, it reads it. It is this Mac's preference for what this Mac computes: a render it lends to another Mac follows its switch, one it borrows follows the lender's (a job carries no switch). `status` gives it as `"neural_engine"` (`true` or `false`), and each image's line carries `"neural_engine"` (the Neural Engine's share of the render, 0 to 1), absent when the Neural Engine was not used. `set save-images FOLDER|off` is Settings › General's Save Every Image To…, off by default: each new image of the history (a render, a series' cell, a crop, an enlargement) is also written to that folder as a PNG with its metadata, under its `save` name; the folder must exist, it is never created; alone, `set save-images` reads it. `set glass [on|off]` is Settings › General's Glass, on by default: the chain and the history over the image, glass or opaque (`AppState.glass`); alone, it reads it. `set updates [on|off]` is Settings › General's Check at Launch, on by default (`Updates.atLaunch`); alone, it reads it. `set preview [on|off]` is the DiT box's « Preview every step » (`AppState.previews`), the window's for the session; alone, it reads it. The arguments of `add` and `grid`, `rewrite`, `describe` and `set` are read in the library (`AddOrder`, `WriterOrder`, `SetOrder`, `BetaOption`), where the tests read them — `measure`'s renders too, `add` lines whose prompt follows a lone `--`.

**The history, the series, the models and the library are the window's too.** Each of these calls the function the button or the menu item calls, with the guard the window puts on it: what is greyed out in the window is a refusal here, with the same sentence. `remove i7 [i8 …]` is `AppState.delete` (⌫), `undo [--redo]` the window's own `UndoManager` (⌘Z, ⇧⌘Z: removals, crops, a prompt carried to the rack), `again <i7|file.png>` is `redo` (⌘R, Render Again) and, from a PNG that Siliconed wrote, `restoreSettings(fromPNG:)` as a drop does it, then Generate; `reuse` is Reuse These Settings, without the render. A series has its tile's two gestures: `remove g2` is « Remove Series from History » (`removeSeries`, undone by `undo`), `reuse g2` « Reuse This Grid » (`restoreSettings`). A gesture that queues jobs answers with them (on a followed Mac each is answered by that Mac, as `vary` does). `crop i7 --box X,Y,W,H | --ratio P:Q` asks the editor's own frame rules (`Crop.Frame`, `CropSpec` in the library) and the same `commitCrop` that Return calls; `save` writes PNG, JPEG and HEIC as the Save and Export panels do. A grid's cell is named `g2c3` (the grid, then its rank in the sheet's reading order from 0, the same arithmetic as the job's `column` and `row`; its job `t5` names it too); `sheet g2 FILE.png|FOLDER` is « Export Sheet… » (`writeSheet`), on any series of the session, ended or not: a cell not rendered yet is drawn empty, and while no cell has an image there is no sheet (`cell`). `install ID [--standard|--compact]` opens the Models sheet on the model, its license and what is left to download, and downloads nothing: the user reads, then accepts in the window; naming a version that is whole on disk beside the one rendered switches to it at once, with no sheet. `status` follows the installation (`"installing"`: the line the window shows, `received_bytes` and `total_bytes`). `import FILE.safetensors …` is `perform` (a drop on the window): each file is recognized by its tensors, as a LoRA or as the model of one family, before any is copied, so a refusal comes back as the command's failure, not as a sentence in a window nobody looks at, and imports nothing (`import_refused`, `import_base_model`, `import_deeper_model`, `unsupported_lora`; `import_needs_family` for a model whose family is not installed: install it first, an import downloads nothing). An imported LoRA is then named by `add --lora NAME[:STRENGTH]`. `uninstall ID [--variant standard|compact]|downloads|legacy` is the sheet's Uninstall, the removal of one version alone, Discard for the interrupted downloads, and Free… for the files of version 0.21 (`releaseLegacy`); `install stop` is its Stop. `macs` lists the paired Macs and their state, `compute NAME|this` is the Compute On menu (`MainWindow.compute(on:)`), `macs connect|disconnect` are Settings › Macs › Other Macs' buttons. `library move DIR|home` is Move Library… and Move Back to This Mac, `open DIR` and `local` the two buttons beside them.
**What destroys or moves things needs `--yes`**: `uninstall` and `library move|home`. Without it the answer is a `dry_run` that says what would go, or what would be copied, and the room it frees or takes (`LibraryMove.plan`, the same function the move starts with, so the two cannot disagree). The refusals are the sheet's and Settings': a render or an installation running (`busy`), the library's disk absent (`library_absent`). **On a followed Mac** the sheet asks the other Mac and waits for a click on its screen; the commands do not wait for a click that is not theirs: `install`, `import`, `uninstall` and `library move|home` are refused there (`remote`). Never a pairing, a loan or a forgetting. What has no command is display, not a gesture: the comparison curtain, the components moved aside, the Chain inspector, the image's details, Share and Copy, the rack's other fields (`add` is the form and Generate in one), and the window's sheets (they only show what a command answers).

## The command

`silicontrol` ships inside the app, at `Siliconed.app/Contents/Helpers/silicontrol` (target `Silicontrol`, `App/Sources/Silicontrol/main.swift`). Settings › Advanced › Command Line (“Install…”) links it into `/usr/local/bin`. It is a pipe: Foundation and the system's frameworks only, it does not link the engine. Its neighbour in `Contents/Helpers`, `siliconed`, is another command: the one for the checks and the library, which does not talk to the open app. If the app is not running, any command but the help launches it and waits for its socket (30 s at most); `silicontrol open` does only that. The help (`help`, `help <topic>`, `<command> --help`, no argument) is answered by the command itself, without launching the app.

## The socket and the protocol

- **Unix socket** `silicontrol.sock` in the app's space (by default `~/Library/Application Support/Siliconed/silicontrol.sock`, or under `SILICONED_ROOT`) — there even when the library was moved to another disk —, mode `0600`: only the account that launched the app can open it. No network port. It disappears when the app quits; a dead socket is replaced at the next launch, and a second Siliconed on the same library does not listen.
- **One connection per command.** The client writes one JSON line, `{"argv": ["add", "--batch", "2", "…"], "cwd": "/current/folder"}`, and the app answers with JSON lines, then closes. Intermediate lines carry `"type"` (`added`, `image`, `sheet`, `start`, `stage`, `step`, `end`; `started`, `loading`, `text` for `rewrite` and `describe`; `started`, `progress` for `library move`; `render` for `measure`, which the client writes itself); the last one carries `"ok"` (`true` or `false`, with `"error"`, `"message"` and often `"hint"` on failure). Without the client: `printf '{"argv":["status"]}\n' | nc -U ~/Library/Application\ Support/Siliconed/silicontrol.sock`.
- **All parsing is in the app** (`App/Sources/SiliconedApp/RemoteControl.swift`): `argv` is the command line as typed and the client is only a pipe. Every command reads its flags one way (`Flags.scan`, `App/Sources/Measurement/Flags.swift`): a word of two dashes the command does not take is refused by name wherever it stands, and a text that begins with `--` goes after a lone `--`, past which `--help` is a word too. Only `open`, the help and `measure` are handled client-side: the first two have to work when the app is closed; `measure` is a series of renders that the client drives itself, each an `add --wait` on the socket, timed, while it samples the app's memory (`App/Sources/Measurement`). Relative paths resolve against `cwd`. The images of an edit (`--ref`, repeatable, in order: the first is image 1, the one edited) travel the same way, as paths or history names (`i7`), never as pixels: the app reads them itself.
- **Help has one source**, the module `SilicontrolHelp` (`App/Sources/SilicontrolHelp/`, five files by subject, each page one couple of English and French, `RemoteControlHelp.Page`, Foundation only), linked by both sides: `silicontrol` answers from it without the app, and the app answers from it on its socket (`nc -U` gets the same pages). The language follows the user's preferred order between English and French. The answer is `{"ok": true, "help": "<text>"}` and the client prints the text raw; an unknown topic is a usage failure (`"error": "usage"`, the topics in `"hint"`, exit `2`). Commands, flags, JSON keys and error codes are English in both languages. When a command changes in the app, its help changes in the same commit.
- **Exit codes** of the client: `0` the last line says `"ok": true`; `1` it says `"ok": false`; `2` usage error; `3` the app cannot be reached (not running and not launchable, or not answering).
- **Signals.** The `AppState` emits `Signal` (`started`, `stage`, `step`, `image`, `finished` with its `Issue`, `gridEnded` when a grid's last cell ended) to whoever subscribes; `wait` and `follow` subscribe for the length of their connection and unsubscribe at the first write that fails (client gone).
- **SIGPIPE is ignored** (`signal(SIGPIPE, SIG_IGN)`, plus `SO_NOSIGPIPE` on each client socket), so that a client hanging up cannot kill the app: measured, a client that connected and closed without reading used to take the app down.
- **The plumbing stays off the main thread**: accepting and reading run on background queues (`Socket`, `Connection`), writing on each client's own queue, so a long `wait` blocks neither the app nor other clients. Only the commands run on the main thread, like a click.

## What gets measured

- **`silicontrol measure` is the series anyone can redo on their Mac**, with the app alone (`App/Sources/Measurement/Runner.swift`). The queue must be idle (`busy` otherwise); then a load render, whose time is reported apart, a witness, the N renders, a witness again. The witness is always the default prompt at seed 42: the gap between the two bounds the machine's drift, and beyond 13 % the series says itself that it compares to no other. Each render is timed from the request to the PNG on the client's clock, while a thread reads every 100 ms the memory footprint (`phys_footprint`) of the app that answered on the socket and of its engine's process (`silicore-worker`, its child) together, and keeps its maximum (`Probes`); the pages swapped out and the bytes read from disk are counted. The Mac is kept awake for the series. Each render makes one `"type": "render"` line and one line of the TSV, the load and the witnesses included, with the model, its version, the chip, the memory, macOS, the power source, the thermal state, the Neural Engine switch and B; the verdict carries the summary (`"summary"`) and the TSV's path. The options and the columns are in `silicontrol help measure`.
- **A series' pixels**: each PNG is decoded and its 8-bit RGB pixels hashed (`md5`). Within a series with the Neural Engine off, one prompt at the same seed and the same size must give the same hash: `"bits_stable"` says so, and `false` is then a defect to report, not a measure; with it on the Neural Engine's share may move from one render to the next, and the pixels with it (the summary's note says which). From one macOS to the next the bits can change ([the engine](ENGINE.md#core-ai)): a hash compares only on the same system.
- **App Nap**: in the background, macOS throttles an app. This one holds a "render" activity (`ProcessInfo.beginActivity`) from the first job started until the queue is empty, so that a render asked by the command is not throttled while the window sits behind the others.

## Another process that renders

One render per machine: the engine takes a lock (`/private/tmp/siliconed-render.lock`) for each render, so another process using the engine (a build from source, say) is refused with `render_already_running` while the app renders, and the reverse (two models in the same memory: the system would swap and both timings would mean nothing). Such a program can queue its render in the app with `silicontrol add` instead.
